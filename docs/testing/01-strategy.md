# راهبرد و نتیجه‌ی آزمون

## ۱. سطوح آزمون

| سطح | ابزار | دامنه |
|---|---|---|
| واحد | Vitest | محاسبه‌ی نمره/میانگین، تاریخ تهران، اعتبارسنجی، رمز، TOTP، صف آفلاین |
| یکپارچه‌ی API | Vitest + `app.inject()` + PGlite واقعی | ۱۳ فایل، همه‌ی مسیرهای حساس، RBAC، RLS، idempotency، پشتیبان، سرو SPA |
| رابط کاربری | Vitest + jsdom + `fake-indexeddb` | کامپوننت‌های پایه (شامل پایداری فوکوس مودال)، API client، صف آفلاین، راهنمای تک‌فایل |
| بار | autocannon + هارنس اختصاصی (`apps/api/test/load/run-load.mjs`) | ۵ سناریوی مسیر داغ — روی **PostgreSQL 16.2** (`load-report-real-pg-2026-10-23.json`) |
| بازیابی | scriptهای `db:backup` / `db:restore` | پشتیبان ۳۲ جدول/۱۱۸٬۲۱۱ ردیف → بازیابی روی نمونه‌ی دوم PostgreSQL + آزمون ورود (`04-real-postgres-restore.md`) |
| مرورگر واقعی (E2E) | Chromium headless ۱۳۱ + puppeteer-core | نسخه‌ی HTML تک‌فایل ۷/۷ PASS (`02-standalone-html.md`) و کل جریان‌های محصول ۲۳/۲۳ PASS (`03-product-e2e.md`) شامل قطع واقعی شبکه و PWA آفلاین |

## ۳. آزمون بار (مشورتی، نه تعهد ظرفیت)

محیط: PGlite تعبیه‌شده (تک‌اتصال، بدون موازی‌سازی واقعی)، ۲۰ اتصال هم‌زمان، ۱۰ ثانیه،
سرور Node 22 روی همین سندباکس. گزارش خام: `docs/testing/load-report-2026-10-23.json`.

| سناریو | درخواست | rps | میانگین | p99 | کدها |
|---|---|---|---|---|---|
| فهرست کلاس (زنگ) | ۱٬۸۳۵ | ۱۸۴ | ۱۰۸ ms | ۱۷۱ ms | 100% 2xx |
| ثبت حضور گروهی (۳۰ دانش‌آموز، POST) | ۱٬۱۱۹ | ۱۱۲ | ۱۸۰ ms | ۲۳۰ ms | 100% 201 |
| ثبت نمرات ارزیابی (POST) | ۱٬۵۶۷ | ۱۵۷ | ۱۲۶ ms | ۱۷۵ ms | 100% 2xx |
| داشبورد مدیر | ۸۳۴ | ۸۳ | ۲۳۷ ms | ۳۰۶ ms | 100% 2xx |
| `/api/meta/options` | ۲٬۵۱۲ | ۲۵۱ | ۷۹ ms | ۱۶۴ ms | 100% 2xx |

تفسیر صادقانه:

- اوج واقعی مدرسه در زنگ اول حدود ۵۰ کلاس × ۱ ثبت است، یعنی ده‌ها درخواست در چند ثانیه —
  بسیار پایین‌تر از ظرفیت اندازه‌گیری‌شده.
- این اعداد روی **PGlite** و در یک سندباکس مشترک گرفته شده‌اند؛ روی PostgreSQL مدیریت‌شده‌ی
  واقعی عدد متفاوت (معمولاً بهتر در نوشتن موازی) خواهد بود و باید دوباره سنجیده شود.
- اعداد به‌عنوان «تعهد SLA» ارائه نمی‌شوند.

## ۴. آزمون‌های امنیتی که انجام نشده‌اند

- تست نفوذ مستقل، اسکن DAST، بازبینی وابستگی با ابزار سازمانی — **NOT RUN**.
- آزمون دسترس‌پذیری با صفحه‌خوان واقعی (NVDA/VoiceOver) — **NOT RUN**؛ فقط بررسی ساختاری
  (برچسب‌ها، `aria-*`، اندازه‌ی ناحیه‌ی لمس، کنتراست رنگ‌ها در CSS) انجام شده.
- آزمون چاپ کارنامه در چاپگر واقعی — **NOT RUN**.

## ۵. اجرای آزمون‌ها

```bash
npm run typecheck
npm run lint
npm run test:api          # نیاز به PGlite؛ پورت را خودش انتخاب می‌کند
npm run test:web
# آزمون بار (سرور جدا روی پورت ۳۱۰۰ لازم است):
BASE_URL=http://127.0.0.1:3100 LOAD_CONNECTIONS=20 LOAD_DURATION=10 \
PGLITE_DIR=/tmp/pglite-load PGLITE_PORT=55440 PORT=3100 RATE_LIMIT_MAX=500000 \
LOGIN_RATE_LIMIT_MAX=5000 node apps/api/test/load/run-load.mjs
```

> هارنس بار برای هر درخواست نوشتن، داده و کلید یکتا می‌سازد و توزیع کدهای وضعیت را
> گزارش می‌کند. نسخه‌ی اول هارنس `non2xx` را از شمارنده‌ی autocannon می‌خواند و گمراه‌کننده
> بود؛ اکنون هر درخواست صریح شمرده می‌شود (`statusCodes`).
